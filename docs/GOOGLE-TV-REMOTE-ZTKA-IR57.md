# Google TV Remote（ZTKA-IR57）适配说明

本文件记录在这台遥控器上**实测确认**的协议事实、固件里对应的实现位置，以及排查问题时该看哪一行日志。
所有结论都来自设备日志，不是推断；凡是被实测推翻的早期结论，记在最后一节。

遥控器信息：

| 项 | 值 |
| --- | --- |
| 广播名 | `Google TV Remote` |
| 型号（GATT Device Information `0x2A24`） | `ZTKA-IR57` |
| 地址 | `c4:19:d1:9b:6c:a9`（公用地址，`addr_type=0`） |
| 按键数 | 15 |

---

## 1. 按键：两条 HID 报告，两套独立索引

**这是本遥控器最容易踩的坑。** 它暴露了**两条 HID Report 特征**，各自有**互相独立的按键编号空间**：

| 报告 | 特征句柄 | 报文形状 | 索引含义 |
| --- | --- | --- | --- |
| 主报告 | `0x0021` | `[idx, 0]`（2 字节） | 1 上 · 2 下 · 3 左 · 4 右 · 5 确认 · 6 返回 · 7 home · 9 静音 · 10 YouTube · 11 Netflix · 12 电源 · 13 输入源 |
| 副报告 | `0x001D` | `[idx, 0, 0, 0, 0, 0]`（6 字节） | 1 音量+ · 2 音量− |

主报告索引 8 未被本遥控器使用；副报告只有 1 和 2。

**索引只在同一条报告内唯一。** 索引 1 在主报告里是「上」，在副报告里是「音量+」；
索引 2 在主报告里是「下」，在副报告里是「音量−」。

> 曾经把两者拍平成同一套「索引 → 槽位」表，后果是：
> 按**音量+**跑的是**电源**的动作，按**方向下**跑的是**语音助手**的动作。
> 表现成「好几个键都触发语音助手」——因为「方向下」和「语音」被解析成了同一个槽位。

### 实现

`main/ble/ble_remote_client.c`：

- `GTV_REPORT_SECONDARY`（= 0）标出哪一条是副报告。**这是推出来的，不是猜的**：
  设备发现阶段按句柄顺序订阅 `0x001D`（数组下标 0）和 `0x0021`（下标 1），
  而抓到的每一个 2 字节按键报文都出现在 `NOTIFY: handle=0x0021`，所以 6 字节的
  音量报文只能来自 `0x001D`。
- `google_tv_index_to_key(chr_index, index)` 以 `(报告, 索引)` 为身份，映射到**共享的规范键码**
  （`MI_KEY_UP`、`MI_KEY_VOICE`…）。用共享键码的好处是每个键自然落到与小米遥控器
  相同的物理槽位上，因此内置槽位名和出厂键盘映射都不用改。

### 语音助手不在 HID 报告里

**语音键不发任何 HID 报告。** 它只在 ATVV 控制特征（句柄 `0x003A`）上发一个
`AUDIO_START`（`0x04`，后面跟 `0x03`、codec、session），日志形如：

```
NOTIFY: handle=0x003A len=4 [04 03 01 3E]
ATVV: Voice start (session 62, codec 1)
USB_HID: Emit action type=7 mod=0x40 key=0x36     <- 语音热键
```

固件里 `handle_atvv_ctl()` 把它转成一次 `MI_KEY_VOICE` 按下，再走键盘映射的
`ACTION_VOICE_HOLD`。**因此不要把语音键加进 `google_tv_index_to_key()`** ——
加了会变成第二条竞争的触发路径。

## 2. 麦克风链路

```
遥控器 --ADPCM 8 kHz--> BLE ATVV 特征 0x0037
   -> atvv_audio.c 判定封装（本遥控器是"裸流"，无 ATVV 头）
   -> audio_pipeline_feed_adpcm()  解码 + DSP + 环形缓冲
   -> audio_pipeline_read_for_usb()
   -> uac_microphone.c  uac_stream_task()  每 2 ms 提交一包
   -> USB 等时 IN 端点 0x81  ->  Windows
```

**测得的数据率：** 每包 14–20 字节、约 200 包/秒 → 4000 B/s，正好是
8 kHz / 16 bit @ 4:1，所以固件按 `AUDIO_SAMPLE_RATE 8000` 构建。
`MIC_OPEN` 请求的是 codec `0x0002`（16 kHz），遥控器实际用 `codec 1`（8 kHz）回，
以遥控器为准。

### UAC 是主机驱动的

**主机不打开采集流，固件一个字节都发不出去。** 只有应用真的开始录音，Windows 才发
`SET_INTERFACE alt=1`；此前端点停在 `alt=0`（零带宽）。这不是 bug，是 USB 音频的规矩。

### 采样率改动会让 Windows 端点失效（重要）

Windows 把每个录音端点的**默认格式**缓存进注册表，按**设备实例（VID/PID/序列号）**索引，
并且**用这个缓存格式以共享模式打开采集流**。改了描述符里的采样率却没改设备身份，就会出现：

| | |
| --- | --- |
| Windows 缓存 | 16000 Hz / 1 ch |
| 设备声明 | 8000 Hz / 1 ch |
| 结果 | `IAudioClient::Initialize` 失败 → 应用报 `NotReadableError` → **主机连 `alt=1` 都不发** |

特征现象是：日志里**一次 `alt=1` 都没有**，`AUDIO: Session:` 行的 `usb_reads=0`，
但 `peak_out` 是正常语音电平。

**固件的处理方式**（`main/usb/usb_descriptors.c`）：把采样率编进 USB 序列号，
格式一变就等于换了新硬件，Windows 会按当前描述符重建端点：

```
84C7BB5A7004-8000        # MAC + AUDIO_SAMPLE_RATE
```

**改采样率时不需要手工做任何事**，这是自动的。副作用是旧端点会变成
`NOT PRESENT` 的幽灵项（不出现在声音设置里）。

### 实测的音频质量与三处 DSP 缺陷

**测量方法**（可复现）：`mic-test.html` 抓**原始 PCM**（故意不用 MediaRecorder ——
有损编码会把要找的缺陷糊掉）POST 到本机，再用 `analyze_audio.py` 量化。判据是：
设备输出 8 kHz，所以**正确的录音在 4 kHz 以上必须没有任何能量**；而 2–4 kHz 是辅音
所在，应当占语谱能量的百分之几。

一次 9.9 秒采集（安静 1 秒 + 稳定元音 + 一句话）的实测：

| 指标 | 实测 | 判读 |
| --- | --- | --- |
| 4 kHz 以上能量占比 | **0.01%** | ✅ 主机侧干净：无混叠、无重采样镜像、无采样率错误 |
| 基频 | **141 Hz** | ✅ 男声「啊」范围。若以 2 倍速送出会是 ~280 Hz |
| 跳变（\|step\|>0.25） | 3 次/秒 | ✅ 无丢帧、无爆音 |
| 峰值 / RMS | 0.42 / −13.2 dBFS | ✅ 电平健康，未削波 |
| **2000–3000 Hz** | **0.31%** | ❌ 应有百分之几 |
| **3000–4000 Hz** | **0.04%** | ❌ 几乎完全缺失 |
| 0–200 Hz | 44.3% | 低频偏重（元音本身 + 可能的握持噪声） |

**结论：2–4 kHz 几乎被抹掉，而那不是麦克风的问题 —— 是固件自己加的滤波器。**

三处缺陷，均已修复：

| # | 位置 | 缺陷 | 实测影响 |
| --- | --- | --- | --- |
| 1 | `audio_pipeline.c` 调 `audio_filter_lowpass` | 3 抽头 `[0.25 0.5 0.25]`，响应是 `cos²(πf/fs)`：**1454 Hz 处 −3 dB、2.5 kHz 处 −10 dB、3.4 kHz 处 −25 dB、4 kHz 处硬零点** | 正好删掉辅音所在频带，是上表 2–4 kHz 缺失的直接原因。**已移除** —— 8 kHz 流本身已被限带到 4 kHz，带内滤波无法把噪声和语音分开，只能删语音 |
| 2 | `audio_pipeline.c` 调 `audio_filter_declip` | 同侧邻点去尖峰，**没有绝对幅度门限**，任何实际幅度都会触发 | 干净正弦上改写 12.5–50% 采样；在 fs/4（2 kHz）处退化，把音调**归零到 −36 dB**。ADPCM 流本来不可能含脉冲尖峰。**已移除** |
| 3 | `app_config.h` 的 AGC 参数 | 噪声门 1000、最大增益 4.0 → 静音时包络跌到门限，增益**钉死在 4.0（+12 dB）** | 每个停顿处把本底噪声抬高 12 dB —— 这就是「语音里有很多杂音」的主要来源。**已改为近中性限幅器**：门限 10000、最大增益 1.2，并补上最小增益 0.35 的下钳位 |

另外两处修正：

- **`MIC_OPEN` 请求的 codec 与编译时的采样率不一致**：一直请求 `0x0002`（16 kHz），
  而 `AUDIO_SAMPLE_RATE`、UAC 描述符、等时包长全是 8 kHz。本遥控器忽略该请求
  （照发 codec 1）所以没暴露；**一旦有遥控器照做就会被半速解码**。现改为由
  `AUDIO_SAMPLE_RATE` 推导。
- **引导静音 150 ms 是真正发出的数字静音**，而会话由**按键**触发（不是由音频触发），
  所以那 150 ms 就是用户第一个字的一部分。已缩短到 20 ms，淡入改为 4 ms。

> 顺带纠正一个**看起来像阻塞性缺陷、实际是误报**的结论：有人把 UAC1
> `FORMAT_TYPE_I` 描述符判成损坏（`tSamFreq = 2048001 Hz`），理由是「长度 0x0B 且多了
> 一个 0x01」。那是漏掉了 **`bSamFreqType`** 字段 —— 该描述符是 `8 + 3N` 字节，
> 第 8 个字段就是 `bSamFreqType`（本处为 1，表示一个离散频率），采样率从第 9 个字节
> 开始。按完整布局解码：`bLength=0x0B`、`bSamFreqType=1`、`tSamFreq=8000`，**完全正确**；
> 独立佐证是 Windows 自己解析该描述符后建立的端点缓存格式正是 8000 Hz。
> 若照那份建议改（长度改 0x0A 再删掉那个字节）反而会破坏一个正常工作的描述符。

## 3. 按键名称与「按键学习」

每个物理槽位可以有一个用户自定义名字，用于**显示**；功能仍然由键盘映射决定。

| WebUSB 命令 | 码 | 载荷 |
| --- | --- | --- |
| `CMD_KEY_NAMES_GET` | `0x27` | 空 → `{"names":["", …]}`，固定 16 项，槽位顺序 |
| `CMD_KEY_NAMES_SET` | `0x28` | `{"slot":0..15,"name":"…"}` → 返回整张表 |

- 空名字 = 用内置名。名字按 **UTF-8 31 字节**截断，且**不切开多字节字符**。
- 存在 NVS 命名空间 `key_names` 的单个 blob（16 × 32 字节）。
- 网页「按键学习」页靠轮询 `CMD_KEYMAP_TELEMETRY` 的 `pressed_vk` 定位槽位，
  `pressed_vk` 是 `k_slot_keys[slot]`，顺序与 `PHYSICAL_KEYS` 完全一致。

## 4. Flash 磨损

原则：**运行时状态不落盘，只有配置落盘。**

| 写入路径 | 触发 | 处理 |
| --- | --- | --- |
| NVS 布局标记 | 仅首次 | 一次 |
| BLE 配对信息 | 仅绑定 MAC 变化（=重配） | 已有变化检测 |
| 键盘映射保存 | 网页改配置 | 逐键比对，**无变化则连 `nvs_commit` 都不调用** |
| 切层 | 每次切层 | **完全不写**（曾经重写整个键盘映射！） |
| 按键名称 | 改名 | 归一化后比对，**没变不写**；连续改合并成一次（200 ms） |

**不写 flash 的：** 日志（`app_log` 只在 RAM）、遥测/状态轮询、电量刷新（GATT 读）、
音频统计、LED 状态。

**NimBLE 的配对库**（`CONFIG_BT_NIMBLE_NVS_PERSIST=y`）绕过 `config_store` 直接写 NVS，
实测重连 + 加密前后 NVS 条目数**不变**，即重连不重写 bond。

### 磨损量表

开机和每 5 秒的 HEALTH 行都带 NVS 已用条目数：

```
INIT: NVS: boot: used=156 free=1860 total=2016 entries
HEALTH: rx=0 total=0 … layout=google_tv nvs=156
```

读法：**正常使用时它不动 = 没有东西在写 flash。** 改配置时会跳。
故意用分区级统计（`nvs_get_stats`）而不是自己计数——自己数看不到 NimBLE 的写入。

## 5. 排查速查表

| 日志行 | 看什么 |
| --- | --- |
| `HOGP: button chr#N idx=M -> key 0xXX (name) DOWN` | `chr#1`=主报告，`chr#0`=副报告。索引对不上就查第 1 节 |
| `HOGP: rx#N len=.. [..]` | 前 32 次按键的原始报文 |
| `LEARN: chr#N len=.. [..]` | 打开 raw report 后，每次**不同**报文打一行（按住不刷屏） |
| `ATVV: Voice start (session N, codec X)` | 语音键按下（ATVV 路径） |
| `ATVV: audio: N packet(s) -> 0 frame(s)` | **`0 frame(s)` 是正常的**，那只统计带 ATVV 头的帧；本遥控器是裸流 |
| `AUDIO: Session: blocks=.. queued=.. peak_in=.. peak_out=.. usb_reads=..` | **`peak_out` 看解码是否出音，`usb_reads` 看主机是否在取数据** |
| `UAC: Host SET_INTERFACE itf=1 alt=N` | `alt=1` 才代表主机开始采集 |
| `HEALTH: … nvs=N` | flash 磨损量表 |

`AUDIO: Session:` 的四种组合：

| `alt=1` | `peak_out` | `usb_reads` | 结论 |
| --- | --- | --- | --- |
| 否 | – | 0 | 主机没开始采集（Windows 侧问题，见第 2 节） |
| 是 | 0 | >0 | 解码出来是静音 → 查解码/DSP |
| 是 | >0 | 0 | 流开了但没喂端点 |
| 是 | >0 | >0 | 音频已在送，问题在主机侧音量/应用 |

## 6. 被实测推翻的结论

留在这里是为了不再走一遍。

1. **「索引 1 是电源、2 是语音、3 是上…」的标准顺序表。** 本遥控器不是这个顺序，
   而且有两条独立索引空间。见第 1 节。
2. **「索引 N → 槽位 N−1 是恒等映射就够了」。** 对单报告遥控器成立，对这台不成立：
   两条报告的索引会撞车。
3. **「`0 frame(s)` 说明语音不通」。** 那个计数器只统计符合 ATVV 封装的帧；
   本遥控器发裸流，所以它**恒为 0**。当时把它当成"工作正常"或"完全不通"的证据都是错的，
   该看的是 `peak_out` 和 `usb_reads`。
4. **「语音键是某个 HID 索引」。** 它根本不发 HID 报告，只发 ATVV `AUDIO_START`。
5. **「切层写 1 字节已经够省了」。** 当时它写的是**整个键盘映射**（5 个层 blob + 切换表）。
   而切换表把切层变成了一次按键。
6. **「麦克风不动是 Windows 权限问题」。** 权限是 Allow。真因是端点格式缓存，
   见第 2 节。
